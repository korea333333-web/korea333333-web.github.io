Anthropic, Claude Code가 컴퓨터 명령을 기본 실행하지 못하게 하는 ‘제한 모드’ 추가

Anthropic이 AI 코딩 도구 Claude Code에 ‘제한 모드’를 추가했다. 이 모드에서는 AI가 작업 폴더의 파일을 살펴보고 고칠 수 있지만, 프로그램과 컴퓨터 명령을 실행하는 기본 도구와 웹페이지를 가져오는 WebFetch는 받지 않는다. 낯선 코드를 먼저 읽혀 보고 실제 실행은 나중에 사람이 결정할 수 있게 한 것이다. 다만 --tools로 도구를 다시 넣을 수 있고 일부 MCP 연결도 남을 수 있어 완전한 격리 기능은 아니다.

낯선 코드는 먼저 읽히고, 실행 권한은 나중에 준다

Claude Code는 Anthropic의 AI가 개발자의 프로젝트 폴더를 읽고 파일을 고치며, 테스트와 컴퓨터 명령까지 실행하는 코딩 도구다. 채팅창에서 설명만 하는 Claude와 달리 실제 프로젝트 안에서 행동할 수 있다.

그래서 실수의 결과도 크다. AI가 요청을 잘못 이해해 중요한 파일을 지우거나, 낯선 저장소에 숨은 지시를 따라 외부 명령을 실행할 수 있다. 실행 전에 허락을 묻더라도 사람이 승인 창을 습관처럼 누르면 보호 장치는 약해진다.

8월 27일 나온 Claude Code 2.1.248 릴리스는 이런 상황에 쓸 새 선택지를 넣었다. 시작 명령에 --restricted를 붙이면 명령과 코드를 실행하는 기본 도구가 목록에서 빠진다. 웹페이지 내용을 가져오는 WebFetch도 함께 빠진다.

쉽게 말해 AI를 컴퓨터 앞에 앉히되 ‘프로그램 실행’ 열쇠는 기본 도구함에서 빼 둔다. Claude는 시작한 작업 폴더 안의 파일을 읽고 다룰 수 있지만, 터미널에서 프로그램을 돌리거나 WebFetch로 웹페이지를 가져오는 길은 기본으로 닫힌다. 다만 다른 MCP 도구와 시작할 때 따로 넣은 도구는 별도로 확인해야 한다.

제한 모드는 사용자·프로젝트·로컬 설정 파일도 무시한다. 낯선 프로젝트에 저장된 설정이 Claude의 행동을 바꾸는 길을 줄이기 위해서다. 모든 승인을 건너뛰는 bypassPermissions도 받아들이지 않는다.

‘파일만 다룬다’는 말의 정확한 뜻

제한 모드가 무조건 읽기 전용이라는 뜻은 아니다. 작업 폴더 안에서는 허용된 파일 도구로 내용을 고칠 수도 있다. 정말 읽기만 시키려면 사용할 도구를 Read·Grep·Glob처럼 별도로 더 좁혀야 한다.

‘실행해도 되는지 먼저 묻는다’와 ‘실행 도구가 처음부터 없다’는 전혀 다르다. 앞의 방식은 사람이 잘못 승인하면 명령이 실행된다. 뒤의 방식은 AI가 판단을 틀려도 기본 실행 도구로는 행동할 수 없다.

일반 모드·샌드박스·제한 모드는 막는 방식이 다르다

일반 모드의 Claude Code도 아무 명령이나 곧바로 실행하지는 않는다. 공식 보안 설명에 따르면 수동 모드는 파일 수정·테스트·명령 실행처럼 결과가 남는 일을 하기 전에 사람에게 허락을 구한다.

샌드박스는 명령 실행 기능을 남겨 두고, 대신 파일과 인터넷에 접근할 수 있는 범위를 울타리 안으로 좁힌다. 테스트는 실제로 돌리되 회사 컴퓨터 전체는 보여주고 싶지 않을 때 샌드박스를 쓴다.

제한 모드는 그보다 앞선 ‘읽어 보는 단계’에 알맞다. 코드 설명, 변경 내용 요약, 의심스러운 파일 찾기, 문서 정리처럼 프로그램을 돌리지 않아도 되는 일에 쓸 수 있다. 일본 기술 매체 DevelopersIO도 새 모드를 직접 시험하고 코드 검토나 자동 점검에서 실행 도구를 한꺼번에 빼는 용도를 짚었다.

외부 업체가 보낸 소스 코드를 처음 연다고 해보자. 일반 모드에서는 Claude가 내용을 알아보려고 설치 명령이나 테스트를 제안할 수 있다. 제한 모드에서는 먼저 파일 구조와 위험해 보이는 부분만 설명하게 하고, 실제 실행은 사람이 내용을 본 뒤 별도 환경에서 진행할 수 있다.

자동으로 들어오는 풀 리퀘스트를 요약할 때도 쓸 수 있다. AI는 어떤 파일이 바뀌었고 사람이 어디를 더 봐야 하는지 정리하지만, 빌드 서버에서 마음대로 명령을 돌릴 권한은 받지 않는다. 검토와 실행을 한 단계에서 함께 맡기지 않는 것이다.

프로젝트 안의 설정을 무시하는 것도 중요하다. Anthropic은 과거 Claude를 제품 안에서 통제하는 방법을 설명한 글에서 저장소 설정과 자동 실행 장치가 공격 경로가 될 수 있다고 밝혔다. 제한 모드는 낯선 프로젝트가 미리 넣어 둔 설정을 그대로 따르지 않고 시작한다.

프로그램을 돌리지 않아도 되는 검토부터 맡긴다

가장 쉬운 일은 새로 받은 코드의 ‘지도’를 그리게 하는 것이다. 어떤 폴더가 화면을 만들고 어디에서 결제를 처리하는지, 이번 변경이 어느 기능과 이어지는지 설명하게 할 수 있다. 명령을 실행하지 않아도 사람이 먼저 볼 파일을 좁힐 수 있다.

두 버전 사이의 차이를 쉬운 말로 바꾸게 할 수도 있다. AI가 바뀐 함수와 설정을 읽고 “로그인에 실패했을 때 나오는 안내 문구가 달라졌다”라고 설명하면 개발자가 아닌 기획자도 검토에 참여할 수 있다. 실제 프로그램이 그 설명대로 움직이는지는 테스트로 따로 확인해야 한다.

설정 파일이 많다면 분류 작업도 맡길 수 있다. 쓰지 않는 것으로 보이는 설정, 비밀 정보처럼 보이는 문자열, 오래된 안내 문서를 찾아 목록으로 받는다. 이 단계에서는 파일을 지우지 않고 후보만 받아야 AI가 잘못 골라도 쉽게 되돌릴 수 있다.

설치·빌드·데이터베이스 변경·브라우저 시험이 필요한 일은 제한 모드만으로 끝낼 수 없다. 프로그램을 실제로 움직여야 결과를 알 수 있기 때문이다. 이 기능은 모든 일을 끝내는 모드가 아니라, 무엇을 실행할지 결정하기 전에 코드를 살펴보는 단계다.

파일 수정과 외부 연결은 따로 막아야 한다

이름에 ‘제한’이 붙어도 백신이나 완전한 격리실은 아니다. Claude가 볼 수 있는 작업 폴더에 비밀번호·고객 정보·배포용 열쇠가 있다면 AI도 그 내용을 읽을 수 있다.

파일 도구가 남아 있으면 내용도 바꿀 수 있다. 따라서 ‘이 코드를 AI에게 보여 줘도 되는가’와 ‘AI가 파일을 고쳐도 되는가’를 따로 정해야 한다. 검토만 시킬 때는 읽기 도구만 지정하고 원본이 아닌 복사본에서 시작하는 편이 안전하다.

--tools로 실행 도구나 WebFetch를 다시 넣으면 가능한 행동도 달라진다. 화면에 제한 모드라고 표시되는지만 보지 말고, 시작할 때 실제로 허용한 도구 목록을 확인해야 한다.

외부 연결과 설정이 모두 사라지는 것도 아니다. DevelopersIO의 실제 비교 시험에서는 --restricted만 썼을 때 claude.ai 커넥터를 통한 MCP 서버가 남았다. 외부 연결을 더 좁히려면 --strict-mcp-config도 함께 써야 했다. 사용자·프로젝트·로컬 설정은 무시하지만 조직이 관리하는 설정과 직접 건넨 --settings는 계속 적용됐다.

글로 “하지 마”라고 적는 것과 프로그램으로 막는 것도 다르다. 8월 공개된 사전 논문 When “Do Not” Is Not Deny는 CLAUDE.md에 적힌 자연어 보안 지시 중 상당수가 강제되는 권한 규칙이 아니라 AI가 문장을 어떻게 해석하느냐에 달려 있다고 분석했다.

그래서 경고 문장을 더 세게 쓰는 것만으로는 부족하다. 실행 도구 제거·폴더 분리·네트워크 제한처럼 컴퓨터가 실제로 막는 장치를 겹쳐야 한다. 마지막 승인도 AI가 아닌 사람이 해야 한다.

명령을 막아도 AI의 설명이 정확해지는 것은 아니다. 실제 파일을 빠뜨리거나 정상 코드를 취약점으로 오해하고, 여러 파일의 관계를 잘못 설명할 수 있다. 행동할 권한을 줄이는 기능과 리뷰 품질을 높이는 기능은 서로 다르다.

회사 코드가 어디에서 어떻게 처리되는지도 별도로 확인해야 한다. 제한 모드는 내 컴퓨터에서 AI가 쓸 도구를 줄일 뿐, 데이터 계약이나 보관 정책을 바꾸지 않는다. 민감한 소스라면 조직용 약관·보관 기간·모델 학습 사용 여부를 따로 살펴야 한다.

팀 기록에는 “제한 모드 사용”이라는 한 줄만 남겨서는 안 된다. 어느 폴더에서 시작했는지, 어떤 자료가 들어 있었는지, 읽기와 쓰기 중 무엇을 허용했는지, 외부 도구를 더했는지 적어야 한다. 그래야 문제가 생겼을 때 AI가 실제로 어디까지 할 수 있었는지 다시 확인할 수 있다.

한국 팀은 공개 코드의 복사본으로 먼저 시험할 수 있다

첫 시험은 외부에 공개된 저장소를 복사한 폴더에서 하면 된다. 비밀키와 회사 자료는 넣지 않는다. 제한 모드로 시작한 뒤 “이 프로젝트가 하는 일, 바뀐 파일, 위험해 보이는 부분만 설명해 달라”고 요청한다.

다음에는 명령 실행 도구와 WebFetch가 실제로 빠졌는지 시험한다. 테스트를 돌리거나 웹페이지를 읽어 달라고 했을 때 수행하지 않는지, 작업 폴더 밖 파일을 요청하면 거부하는지 기록한다. MCP 도구 목록과 조직 관리 설정도 함께 본다. 이름보다 실제로 막히는 행동이 중요하다.

AI가 내놓은 설명은 사람이 다시 읽어야 한다. 중요한 파일을 빠뜨렸는지, 정상 코드를 위험하다고 잘못 봤는지, 수정 제안이 요구사항과 맞는지 확인한다. Anthropic의 자동 보안 검토 안내도 AI 검토는 기존 보안 절차와 사람 리뷰를 대신하지 않고 보완한다고 설명한다.

테스트나 실행이 필요해지면 작업을 별도 단계로 넘긴다. 샌드박스·최소 권한 계정·인터넷 제한·기존 CI 검사를 갖춘 환경에서 실행한다. 제한 모드를 해제한 같은 창에 곧바로 모든 권한을 주면 처음에 만든 경계가 흐려진다.

실행 기록에는 모드 이름만이 아니라 허용한 도구 목록, 시작 폴더, AI가 읽을 수 있던 자료, 사람이 승인한 다음 행동을 함께 남기는 편이 좋다. 그래야 나중에 AI가 실제로 어디까지 할 수 있었는지 되짚을 수 있다.

공용 자동화에 넣을 때는 Claude Code 버전도 고정하는 편이 낫다. 업데이트 뒤 기본 도구나 설정을 읽는 방식이 달라질 수 있기 때문이다. 새 버전을 적용하기 전에 같은 시험 폴더에서 명령 실행·폴더 밖 읽기·파일 수정이 각각 어떻게 처리되는지 다시 확인한다.

AI의 검토 결과를 곧바로 코드 병합 승인으로 써도 안 된다. 제한 모드는 AI가 컴퓨터에 할 수 있는 일을 줄이지만, 리뷰가 정확했다는 보증서는 아니다. 기존 코드 담당자의 확인과 자동 테스트, 보안 검사는 그대로 거쳐야 한다.

AI 코딩 도구는 실력뿐 아니라 권한을 얼마나 잘 나누는지도 경쟁한다

이번 업데이트는 Claude가 코드를 더 잘 짠다는 발표가 아니다. 오히려 AI가 할 수 있는 일을 일부러 줄였다. 코딩 AI가 회사 업무 깊숙이 들어오면서 성능만큼 권한을 잘게 나누는 기능도 중요해졌다는 뜻이다.

모든 작업에 제한 모드를 쓸 필요는 없다. 프로그램을 만들고 테스트까지 돌릴 때는 일반 모드와 샌드박스가 더 알맞다. 하지만 낯선 코드를 처음 열거나 많은 변경을 자동으로 분류하고, 검토와 실행을 나누고 싶을 때는 분명한 출발점이 생겼다.

개발자가 아닌 사람도 결과를 함께 봐야 하는 조직에는 이 분리가 특히 유용하다. 제품 담당자는 AI가 정리한 변경 이유와 영향 범위를 먼저 읽는다. 개발자는 실제 실행이 필요한 항목만 골라 보호된 시험 환경으로 넘긴다. 모두에게 터미널 권한을 주지 않고도 검토를 시작할 수 있다.

Claude Code의 제한 모드는 AI에게 코드를 먼저 보여 주고, 컴퓨터를 움직일 열쇠는 나중에 따로 주는 기능이다. 이름만으로 안전이 보장되지는 않는다. 그래도 코드 검토와 실제 실행을 분리할 수 있다는 점은 팀이 바로 시험해 볼 만한 변화다.
