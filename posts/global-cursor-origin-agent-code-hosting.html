Cursor, AI가 고친 코드를 GitHub에 옮기지 않고 저장·검토하는 ‘Origin’ 공개

AI 코딩 도구 Cursor가 코드를 보관하고 팀원이 검토하는 새 서비스 ‘Origin’을 유료 이용자에게 열었다. 이제 Cursor에서 AI에게 수정을 맡긴 뒤 GitHub로 화면을 옮기지 않아도, 바뀐 줄을 비교하고 동료에게 원본에 합쳐도 되는지 물을 수 있다. 쉽게 말해 AI가 코드를 쓰는 곳과 팀이 코드를 보관·검토하는 곳을 하나로 묶은 것이다. 다만 아직 얼리 베타, 즉 정식 출시 전 시험 단계이므로 중요한 프로젝트는 GitHub 원본을 남겨 둔 채 써보는 편이 안전하다.

결제 버튼 하나를 고치는 과정이 짧아진다

쇼핑몰의 결제 버튼이 작동하지 않아 Cursor의 AI에게 수정을 맡겼다고 하자. 지금까지는 수정이 끝난 뒤 GitHub를 열고 바뀐 파일을 다시 찾아 팀원에게 검토를 부탁했다. GitHub는 코드와 수정 기록을 보관하고 여러 사람이 함께 확인하는 대표 서비스다.

Origin은 이 왕복을 줄인다. Cursor 안에서 저장소를 만들 수 있는데, 저장소는 한 프로젝트의 코드와 변경 기록을 함께 두는 온라인 공동 폴더다. AI가 어느 파일을 바꿨는지 보고, 그 수정을 원본에 합칠지도 같은 화면에서 정한다.

새 프로젝트는 Cursor의 Codebase, 즉 코드 모음 화면에서 바로 만들 수 있다. 이미 진행 중인 프로젝트도 가져올 수 있다. 코드를 검색하고, AI가 고치기 전과 후를 비교하고, 자동 검사 결과와 팀원의 댓글을 확인한 뒤 원본에 합치는 흐름이 이어진다.

Cursor는 6월 개발자 행사 Compile에서 이 구상을 먼저 보여 줬다. 이어 8월 17일 공식 변경 기록에서 모든 유료 플랜 이용자에게 Origin을 차례로 열겠다고 밝혔다. 기업 계정은 관리자가 Origin 사용을 막을 수도 있다.

현재 확인된 범위는 저장소 생성, 코드 검색과 팀의 검토 요청 같은 기본 기능이다. 기능과 가격, 운영 방식은 시험 과정에서 달라질 수 있다. 여러 AI가 안정적으로 동시에 일하거나 GitHub의 모든 기능을 대신한다는 뜻으로 받아들이기에는 이르다.

AI가 바꾼 코드는 바로 원본에 들어가지 않는다

팀 개발에서는 원본을 곧바로 고치지 않는다. 먼저 브랜치, 즉 원본과 떨어진 작업용 복사본에서 수정한다. 그다음 풀 리퀘스트(PR), 곧 “이 변경을 원본에 합쳐도 되는지 봐 달라”는 요청을 보낸다. 다른 사람이 내용을 확인해야 원본에 합치는 안전장치다.

예전에는 Cursor에서 AI에게 일을 맡긴 뒤 GitHub로 가서 브랜치와 PR을 확인했다. Origin에서는 AI에게 수정을 맡기고, 달라진 파일을 읽고, 팀원의 의견을 받는 일을 한 화면에서 이어 간다. 같은 오류 설명을 Cursor와 GitHub에 반복해 적는 수고도 줄어든다.

여러 AI가 서로 다른 파일을 동시에 고치면 “왜 이렇게 바꿨는지”를 남기는 일이 더 중요해진다. AI가 받은 지시, 실제 수정 내용과 사람의 댓글이 한 프로젝트에 모이면 문제가 생겼을 때 어느 결정에서 시작됐는지 찾기 쉽다.

코드 관리의 기본 원리 자체가 바뀌는 것은 아니다. Git이라는 변경 기록 방식, 브랜치와 PR은 그대로 쓴다. 달라진 점은 코드를 만드는 AI와 그 코드를 보관·검토하는 화면을 Cursor가 함께 운영한다는 것이다.

코드가 바뀔 때마다 오류를 자동으로 확인하는 지속적 통합(CI)도 연결할 수 있다. Cursor는 Depot·Buildkite를 이용한 자동 검사와 Vercel의 시험용 페이지를 안내했다. 하지만 GitHub에서 쓰던 자동화가 전부 그대로 옮겨오는 것은 아니며, 연결한 외부 서비스 비용도 따로 확인해야 한다.

GitHub는 지우지 말고 먼저 연결해서 써보는 게 낫다

가장 되돌리기 쉬운 방법은 GitHub를 원본으로 둔 채 Origin을 연결하는 것이다. 기존 GitHub 저장소를 연결하면 Cursor가 사본을 가져온다. Origin에서 검색과 검토를 하더라도 새 변경 기록의 최종 목적지는 계속 GitHub로 둘 수 있다.

PR에 남긴 댓글도 양쪽에 반영된다. Cursor에서 쓴 의견이 GitHub에 나타나고, GitHub에서 단 답변도 Cursor로 들어온다. 기존 권한과 자동화, 오랜 기록을 한꺼번에 옮기지 않고도 Origin이 정말 편한지 확인할 수 있다.

GitHub는 단순한 파일 보관함이 아니다. GitHub는 2025년 Octoverse에서 1억8천만 명이 넘는 개발자가 플랫폼을 사용한다고 밝혔다. 문제 신고, 새 버전 공개, 보안 규칙과 다른 서비스 연결이 오랫동안 쌓여 있다. 저장소 주소를 바꾼다고 이 생태계가 한꺼번에 따라오지는 않는다.

Cursor는 AI가 만든 수정 가운데 무엇이 승인되고 거절됐는지를 같은 화면에서 볼 수 있다. 이용자에게는 편하지만, 코드와 검토 기록이 한 회사에 더 많이 모인다는 뜻이기도 하다. 편리함을 얻는 만큼 어떤 자료를 Cursor가 보관하는지 따져야 한다.

출시 당일 GitHub 장애가 있었지만 원인은 아니다

Origin 공개와 GitHub 장애가 직접 연결됐다는 근거는 없다. Cursor는 두 달 전부터 Origin을 예고했고, 이런 서비스를 며칠 만에 만들어 내놓을 수도 없다. 같은 날 일어난 두 사건을 원인과 결과로 묶어서는 안 된다.

Origin이 열린 8월 17일 GitHub가 몇 시간 동안 큰 장애를 겪은 것은 사실이다. Android Central은 웹 화면, 코드 검토, 자동화와 Copilot이 영향을 받았고 원본 파일 다운로드 오류율이 한때 약 50%에 이르렀다고 전했다. 결과적으로 GitHub 밖의 선택지에 관심이 커질 만한 날이었다.

AI 때문에 코드 보관 서비스가 처리해야 할 일도 늘고 있다. GitHub는 저장소 생성과 자동화 요청, 큰 프로젝트 사용량이 빠르게 늘어 2025년 10월부터 용량을 열 배 키우는 계획을 진행 중이라고 밝혔다. 5월 안정성 보고서에서는 AI 보조 도구와 AI 에이전트도 트래픽 증가 요인으로 들었다.

사람 한 명이 하루 몇 번 코드를 올리는 것과 여러 AI가 계속 수정본을 만들고 검사를 요청하는 것은 부담이 다르다. Origin이 이 변화를 겨냥한 서비스라는 설명은 타당하다. 그래도 ‘AI 에이전트용’이라는 이름만으로 GitHub보다 빠르고 안정적이라고 단정할 수는 없다. 실제 이용 기록과 장애 복구 약속이 더 필요하다.

Cursor는 AI가 쓴 코드의 승인 결과까지 알고 싶다

AI 시대에 맞는 코드 보관 서비스를 만드는 회사는 Cursor뿐이 아니다. 전 GitHub CEO 토마스 돔케가 만든 Entire도 AI가 어떤 지시를 받고 왜 코드를 바꿨는지 기록하는 서비스를 개발한다. The Register는 Entire가 GitHub 저장소 사본과 별도 작업 공간을 제공하고, 앞으로 핵심 네트워크를 오픈소스로 공개할 계획이라고 보도했다.

GitLab, Bitbucket, Codeberg 같은 코드 보관 서비스도 이미 있다. Origin의 차이는 새로운 저장 기술을 발명한 데 있지 않다. Cursor의 AI가 코드를 만들고, 사람이 읽고 승인한 결과까지 한 흐름으로 잇는 데 있다.

Cursor가 승인과 거절 기록을 보면 어떤 AI 수정이 실제로 유용했는지 제품 개선에 활용할 수 있다. 팀은 도구를 오갈 필요가 줄어든다. 반대로 Cursor의 장애나 정책 변경이 코드 작성과 검토, 보관을 동시에 흔들 수도 있으므로 외부 검사와 정기 사본은 여전히 필요하다.

정식 도입 전에는 가격·복구·데이터·이동성을 봐야 한다

가격표부터 아직 완성되지 않았다. Cursor는 Origin이 유료 플랜에 포함된 시험 서비스라고 설명한다. 정식 출시 뒤 저장 공간, 데이터 전송량, 팀원 수와 자동 검사 횟수에 어떤 비용이 붙을지는 충분히 공개하지 않았다. 지금 내는 구독료가 앞으로의 전체 비용이라고 볼 수 없다.

장애가 났을 때의 약속도 필요하다. 정상 작동을 얼마나 보장하는지, 백업을 얼마나 자주 만들고 몇 시간 안에 복구하는지 확인해야 한다. 큰 회사는 코드가 저장되는 나라, 회사별 암호화 열쇠 지원과 법정 보존 기간도 봐야 한다.

Cursor는 개인정보 보호 모드에서 코드 데이터를 모델 공급자가 저장하거나 학습에 쓰지 않도록 한다고 설명한다. 하지만 Origin에 맡긴 코드, 수정 기록, 팀 댓글과 AI 작업 기록을 얼마나 오래 보관하고 어디에 쓰는지는 별도 계약에서 다시 확인해야 한다.

떠날 때 무엇을 가져갈 수 있는지도 중요하다. 코드와 기본 수정 기록은 비교적 쉽게 옮길 수 있지만 팀 댓글, 자동 검사 결과, 앱 설정과 AI가 남긴 작업 이유는 빠질 수 있다. 이 자료를 어떤 형식으로 내려받을 수 있는지가 실제로 한 회사에 묶이는 정도를 결정한다.

한 문장으로 보면: Origin은 GitHub를 당장 없애는 완성품이 아니라, Cursor가 AI 코드 작성에 이어 보관과 팀 검토까지 맡기 시작한 시험 서비스다. GitHub 원본을 남겨 둔 채 써봐야 편리함과 위험을 모두 확인할 수 있다.

한국 팀은 작은 내부 도구 하나로 시험하면 된다

회사의 핵심 서비스가 아닌 작은 저장소 하나를 GitHub와 연결해 본다. 같은 작업을 GitHub와 Origin에서 각각 하고, AI가 만든 브랜치와 팀 댓글이 양쪽에 빠르고 정확하게 반영되는지 적는다. 문제가 생겼을 때 GitHub로 즉시 돌아갈 수 있는지도 확인한다.

Cursor 계정, GitHub 연결 앱, 팀 관리자, 자동 검사와 공개 서비스가 각각 어떤 권한을 쓰는지도 정리한다. AI가 코드를 고칠 수 있더라도 실제 고객이 쓰는 프로덕션 서비스에 올리는 최종 승인권은 사람이 갖는 편이 안전하다.

Origin에 접속하지 못하는 상황도 연습한다. 컴퓨터에 내려받은 사본으로 계속 일하고 다른 저장 장소로 보낼 수 있는지 시험한다. GitHub 동기화가 멈추면 어느 쪽 기록을 원본으로 삼을지도 미리 정해야 한다.

AI가 만든 코드는 Cursor 밖의 도구로 한 번 더 검사하는 편이 좋다. 같은 회사의 AI가 만들고 같은 회사의 화면이 평가하면 비슷한 문제를 놓칠 수 있기 때문이다. 오류 검사, 보안 규칙과 담당자 승인이 모두 끝난 뒤에만 원본에 합쳐야 한다.

공개 프로젝트와 금융·의료 서비스는 더 천천히 옮겨야 한다

누구나 참여하는 공개 프로젝트에는 GitHub의 검색, 문제 신고, 참여 기록과 익숙한 다운로드 주소가 큰 자산이다. 외부 참여자에게 새 계정과 화면을 요구하면 Origin의 이점보다 불편이 커질 수 있다. GitHub를 원본으로 두고 관리자만 Origin을 시험하는 방식이 현실적이다.

금융·의료·공공 분야는 코드와 기록이 저장되는 나라, Cursor의 데이터 처리 협력사, 관리자 열람·삭제 기록과 사고 통보 시점을 확인해야 한다. Cursor 편집기의 일반 계약이 Origin이라는 코드 보관 서비스의 책임까지 모두 설명한다고 볼 수는 없다.

반대로 짧게 쓰는 내부 도구나 새 실험 프로젝트는 옮겨 보기 쉽다. 다른 서비스와 얽힌 부분이 적어 실패해도 되돌리기 때문이다. 실제 고객 정보와 비밀번호, 회사의 핵심 비밀은 넣지 않아야 기능 시험과 보안 검토를 나눌 수 있다.

큰 프로젝트에서 여러 AI를 동시에 쓰는 팀은 속도보다 충돌부터 봐야 한다. 여러 AI가 같은 파일을 고치면 수정본은 빨리 늘지만 사람의 검토가 밀릴 수 있다. 누가 어느 부분을 맡고 어떤 일을 먼저 끝낼지 정하는 것이 수정 횟수보다 중요하다.

어떤 프로젝트든 나가는 길을 준비해야 한다. 가격이 오르거나 서비스가 멈췄을 때 코드, 팀 댓글, 자동 검사 결과와 AI 작업 기록을 언제 어떤 파일로 받을 수 있는지 확인한다. 외부 사본과 복구 연습이 있어야 편리함을 누리면서 선택권도 지킬 수 있다.

Origin의 성패는 편리함보다 되돌아갈 수 있느냐에 달렸다

앞으로 나올 가격표와 운영 약속이 첫 시험대다. 무료 플랜 지원, 기업 데이터 저장 지역, 저장 한도와 장애 보상 기준이 공개돼야 회사가 믿고 맡길 서비스인지 판단할 수 있다.

여러 AI가 같은 프로젝트에서 일할 때 충돌을 얼마나 잘 풀어 주는지도 봐야 한다. 실패한 검사를 고치는지, 사람의 승인을 반드시 거치는지, 왜 수정했는지 기록하는지가 실제 가치다. 현장에서 안정적으로 작동해야 ‘AI 시대의 코드 보관 서비스’라는 설명이 광고를 넘어선다.

GitHub와의 양방향 동기화가 오래 유지되고 Origin에서 만든 저장소도 다른 서비스로 쉽게 옮길 수 있어야 한다. 코드뿐 아니라 팀 댓글과 검사 기록까지 내보낼 수 있다면 이용자는 언제든 떠날 수 있다는 확신을 갖고 Origin을 선택할 수 있다.

Origin은 Cursor와 GitHub를 오가던 불편을 줄인다. 그러나 편한 출입문이 비상구까지 막아서는 안 된다. GitHub 원본을 남기고, 최종 승인은 사람이 맡고, 언제든 사본으로 복구할 수 있게 준비한 팀에게만 이 편리함이 안전한 생산성이 된다.
