Cursor, AI가 짠 코드를 저장하고 팀이 바로 검토하는 ‘Origin’ 공개

지금까지 Cursor에서 AI에게 코드를 고치게 한 뒤 팀원에게 보여 주려면 GitHub를 다시 열어야 했다. 새 서비스 ‘Origin’을 쓰면 Cursor 안에서 코드를 저장하고, 무엇이 바뀌었는지 비교하고, 동료에게 “원본에 합쳐도 될지” 검토를 요청할 수 있다. 한마디로 AI가 코드를 짜는 곳과 팀이 보관·검토하는 곳이 하나가 된 것이다. 다만 아직 시험 단계라 중요한 프로젝트를 곧바로 옮기기보다는 GitHub 원본을 남겨 둔 채 써보는 편이 안전하다.

Cursor Origin이 정확히 뭔데?

AI에게 쇼핑몰의 결제 버튼 오류를 고치라고 했다고 하자. 지금까지는 Cursor에서 수정이 끝난 뒤 GitHub를 열어 바뀐 파일을 확인하고, 팀원에게 검토를 부탁해야 했다. GitHub는 코드와 수정 기록을 보관하고 함께 검토하는 대표 서비스다.

Origin은 이 사이의 이동을 줄인다. Cursor 안에서 ‘저장소’를 만들 수 있는데, 저장소란 한 프로젝트의 코드와 수정 기록을 모아 두는 온라인 공간이다. 누가 무엇을 바꿨는지 살펴보고, 변경한 코드를 원본에 합칠지도 같은 화면에서 결정할 수 있다.

새 프로젝트는 Cursor의 Codebase(코드 모음) 화면에서 바로 만들 수 있고, 이미 진행 중인 프로젝트도 가져올 수 있다. 그 뒤에는 코드를 검색하고, AI가 바꾼 파일을 전후로 비교하고, 자동 검사 결과를 보며, 팀원이 댓글을 남긴 뒤 원본에 합칠 수 있다.

Cursor는 6월 개발자 행사 Compile에서 이 구상을 처음 소개했다. 이어 8월 17일 공식 변경 기록을 통해 모든 유료 플랜 이용자에게 Origin을 차례로 열겠다고 밝혔다. 기업용 계정은 관리자가 Origin 사용을 막을 수도 있다.

다만 지금은 ‘얼리 베타’, 즉 정식 출시 전에 실제 이용자에게 먼저 시험을 맡기는 단계다. 기능과 가격, 운영 방식이 달라질 수 있다. 현재 확인된 것은 저장소를 만들고 코드를 검색하며 팀의 검토 요청을 확인하는 기본 기능이다. GitHub를 완전히 대신할 서비스라고 판단하기에는 아직 이르다.

AI가 고친 코드, 팀은 어떤 순서로 확인하나?

팀 개발에는 원본을 바로 고치지 않는 안전장치가 있다. 먼저 ‘브랜치’, 즉 원본과 떨어진 작업용 복사본에서 수정한다. 그다음 ‘풀 리퀘스트(PR)’, 즉 “이 변경을 원본에 합쳐도 되는지 봐 달라”는 검토 요청을 보낸다. 다른 사람이 내용을 확인하고 문제가 없다고 판단해야 원본에 합친다.

기존에는 Cursor에서 AI에게 일을 맡긴 뒤 GitHub로 가서 브랜치와 검토 요청을 확인해야 했다. Origin에서는 AI에게 수정을 맡기고, 달라진 파일을 읽고, 팀원의 의견을 주고받는 흐름을 한 화면에서 이어 갈 수 있다. 같은 설명을 여러 도구에 반복해서 입력하는 수고도 줄어든다.

여러 AI가 동시에 다른 일을 할 때는 기록이 더 중요하다. 결과만 보면 왜 그런 수정을 했는지 알기 어려울 수 있다. AI가 받은 지시와 수정 내용, 사람의 검토 의견이 한 프로젝트에 함께 남으면 문제가 생겼을 때 원인을 찾기 쉬워진다.

Origin이 코드 관리의 기본 원리까지 바꾸는 것은 아니다. Git이라는 변경 기록 방식, 작업용 복사본, 검토 요청은 그대로 쓴다. 달라지는 점은 코드를 만드는 AI와 코드를 보관하는 서비스를 Cursor가 함께 운영한다는 것이다.

자동 검사와 시험용 공개도 가까워진다. 코드를 바꿀 때마다 오류가 없는지 자동으로 확인하는 방식을 ‘지속적 통합(CI)’이라고 한다. Cursor는 Depot·Buildkite를 통한 자동 검사와 Vercel의 미리보기 페이지 연결을 안내했다. 다만 GitHub가 제공하던 자동 검사 기능 전체가 Origin으로 그대로 옮겨오는 것은 아니며, 외부 서비스 비용도 따로 확인해야 한다.

그럼 GitHub를 바로 없애도 될까?

아니다. 가장 안전한 시험 방법은 GitHub를 그대로 두고 Origin을 연결하는 것이다. 팀이 기존 GitHub 저장소를 연결하면 Cursor가 그 사본을 가져온다. Origin에서 코드를 찾아보고 검토할 수 있지만, 새 수정 기록을 올리는 최종 목적지와 원본은 계속 GitHub로 유지할 수 있다.

검토 요청에 남긴 댓글도 양쪽에 반영된다. Cursor에서 쓴 의견이 GitHub에 나타나고, GitHub에서 단 답변도 Cursor로 들어온다. 팀은 기존 권한과 자동화, 과거 기록을 한꺼번에 옮기지 않고도 Origin이 정말 편한지 시험할 수 있다.

이 선택은 GitHub가 단순한 파일 보관함이 아니기 때문에 중요하다. GitHub는 2025년 Octoverse에서 1억8천만 명이 넘는 개발자가 플랫폼을 사용한다고 밝혔다. 문제 신고, 새 버전 공개, 보안 규칙, 다른 서비스와의 연결까지 오랜 시간 쌓여 있다. 저장소 주소 하나를 바꾼다고 이 생태계 전체가 함께 이동하지는 않는다.

Cursor 입장에서도 이 연결은 중요하다. AI가 만든 수정 가운데 무엇이 승인되고 무엇이 거절됐는지를 같은 화면에서 볼 수 있기 때문이다. 그러나 이용자 입장에서는 그만큼 코드와 검토 기록이 한 회사에 더 많이 모인다는 뜻이기도 하다. 편리함과 데이터 통제를 함께 따져야 한다.

GitHub 장애와 같은 날 나왔는데, 관련이 있나?

직접적인 관련은 확인되지 않았다. Cursor는 두 달 전에 이미 Origin을 예고했고, 이런 서비스를 며칠 만에 만들어 내놓을 수도 없다. 두 사건이 같은 날 벌어졌다는 사실과 원인·결과 관계는 구분해야 한다.

다만 Origin이 열린 8월 17일 GitHub가 몇 시간 동안 큰 장애를 겪은 것은 맞다. Android Central은 웹 화면, 코드 검토, 자동화 기능과 Copilot이 영향을 받았고 원본 파일 다운로드 오류율이 한때 약 50%에 이르렀다고 전했다. GitHub 대안을 찾는 관심이 커질 만한 날이었다.

AI 때문에 코드 서비스가 감당해야 할 일이 늘고 있는 것은 사실이다. GitHub는 저장소 생성과 자동화 요청, 큰 프로젝트의 사용량이 빠르게 늘어 2025년 10월부터 용량을 열 배 키우는 계획을 진행 중이라고 밝혔다. GitHub는 5월 서비스 안정성 보고서에서 AI 보조 도구와 AI 에이전트의 활동도 트래픽 증가 요인으로 들었다.

사람 한 명이 하루에 몇 번 코드를 올리는 것과 여러 AI가 계속 수정본을 만들고 검사를 요청하는 것은 부담의 크기가 다르다. Origin이 이런 시대를 겨냥했다는 설명은 이해할 만하다. 다만 “AI 에이전트용”이라는 이름만으로 더 빠르고 안정적이라고 볼 수는 없다. 실제 이용 기록과 장애 대응 약속이 나와야 판단할 수 있다.

왜 Cursor는 코드 보관까지 직접 하려는 걸까?

AI 시대에 맞는 코드 보관 서비스를 만들려는 회사는 Cursor뿐이 아니다. 전 GitHub CEO 토마스 돔케가 만든 Entire는 AI가 어떤 지시를 받고 왜 코드를 바꿨는지까지 기록하는 서비스를 개발하고 있다. The Register는 Entire가 GitHub 저장소의 사본과 별도 작업 공간을 제공하며, 앞으로 핵심 네트워크를 오픈소스로 공개할 계획이라고 보도했다.

GitLab, Bitbucket, Codeberg처럼 코드를 보관하는 다른 서비스도 이미 있다. Origin의 차이는 새로운 저장 방식을 발명했다는 데 있지 않다. Cursor의 AI가 코드를 만들고, 사람이 검토하고, 승인 결과를 남기는 과정을 얼마나 자연스럽게 이어 주느냐가 핵심이다.

한 회사가 코드 작성 AI와 검토 화면, 보관 장소를 모두 운영하면 편리하다. 반면 그 회사의 오류나 정책 변경이 전체 작업에 영향을 줄 수도 있다. 따라서 다른 도구로 다시 검사하고, 외부에 정기적으로 사본을 보관하는 안전장치는 여전히 필요하다.

돈·장애·내 코드·떠날 때 자료, 네 가지를 확인해야 한다

첫째는 가격이다. 현재 Cursor는 Origin이 유료 플랜에 포함된 시험 서비스라고만 설명한다. 정식 출시 뒤 저장 공간, 데이터 전송량, 팀원 수와 자동 검사 횟수에 어떤 비용이 붙을지는 충분히 공개되지 않았다. 지금 내는 Cursor 구독료가 앞으로의 전체 비용이라고 단정할 수 없다.

둘째는 장애와 복구 약속이다. 서비스가 얼마나 자주 정상 작동해야 하는지, 백업을 얼마나 자주 만드는지, 문제가 생겼을 때 몇 시간 안에 되살리는지 확인해야 한다. 큰 기업이라면 어느 나라의 서버에 코드가 저장되는지, 회사별 암호화 열쇠를 쓸 수 있는지, 법에 따라 자료를 얼마나 보관하는지도 중요하다.

셋째는 데이터 사용 범위다. Cursor는 개인정보 보호 모드에서 코드 데이터를 모델 공급자가 저장하거나 학습에 쓰지 않도록 한다고 설명한다. 그러나 Origin에 맡긴 코드, 수정 기록, 팀의 댓글과 AI 작업 기록을 얼마나 오래 보관하고 어떻게 쓰는지는 별도 계약에서 다시 확인해야 한다.

넷째는 다른 서비스로 옮길 수 있는가다. 코드와 기본 수정 기록은 비교적 쉽게 옮길 수 있다. 그러나 팀의 댓글, 자동 검사 결과, 앱 설정과 AI가 남긴 작업 이유는 함께 이동하지 않을 수 있다. 이 자료를 어떤 형식으로 내려받을 수 있는지가 실제 종속 위험을 결정한다.

한 문장 판단: Origin은 GitHub를 당장 대신하는 완성품이 아니라, Cursor가 코드 작성뿐 아니라 보관과 팀 검토까지 맡기 시작한 시험 서비스다. 중요한 프로젝트를 바로 옮기기보다 GitHub 원본을 남겨 둔 채 편리함과 위험을 함께 확인하는 편이 안전하다.

한국 팀은 어떻게 시험하면 될까?

가장 안전한 시험은 회사의 핵심 서비스가 아닌 작은 저장소 하나를 GitHub와 연결하는 것이다. 같은 작업을 GitHub와 Origin에서 각각 해 보고, AI가 만든 작업용 복사본과 팀 댓글이 양쪽에 빠르고 정확하게 반영되는지 기록한다. 문제가 생기면 GitHub로 돌아갈 수 있는지도 함께 확인한다.

누가 어떤 권한을 갖는지도 한눈에 정리해야 한다. Cursor 계정, GitHub 연결 앱, 팀 관리자, 자동 검사와 공개 서비스가 어떤 열쇠를 쓰는지 확인한다. AI는 코드를 고칠 수 있어도, 실제 고객이 쓰는 서비스에 올리는 최종 승인권은 사람이 갖도록 나누는 편이 안전하다.

장애 상황도 미리 연습할 수 있다. Origin에 접속하지 못할 때 컴퓨터에 내려받은 사본에서 작업을 계속하고, 다른 저장 장소로 보낼 수 있는지 시험한다. GitHub와의 동기화가 멈췄을 때 어느 쪽 기록을 기준으로 삼을지도 정해 둔다.

AI가 만든 코드는 Cursor 밖의 도구로 한 번 더 확인하는 것이 좋다. 같은 회사의 AI가 만들고 같은 회사의 검토 도구가 평가하면 놓치는 문제가 비슷할 수 있기 때문이다. 오류 검사, 보안 규칙, 담당자의 승인이 모두 끝난 뒤에만 원본에 자동으로 합치도록 설정해야 한다.

모든 프로젝트를 같은 속도로 옮길 필요는 없다

누구나 참여하는 공개 프로젝트는 GitHub의 검색, 문제 신고, 참여자 기록과 다운로드 주소가 큰 자산이다. 외부 참여자에게 새 계정과 새 화면을 요구하면 Origin의 편리함보다 불편이 더 커질 수 있다. 이런 프로젝트는 GitHub를 원본으로 유지하고 관리자만 Origin을 시험하는 방식이 현실적이다.

금융·의료·공공 분야는 더 조심해야 한다. 코드와 작업 기록이 어느 나라에 저장되는지, Cursor가 데이터 처리를 맡기는 협력사는 누구인지, 관리자 열람과 삭제 기록이 남는지, 사고가 나면 언제 알려 주는지가 중요하다. Cursor 편집기의 일반 계약만으로 코드 보관 서비스의 책임까지 확인됐다고 볼 수는 없다.

반대로 짧게 쓰는 내부 도구나 새 실험 프로젝트는 좋은 시험 대상이다. 다른 서비스와 얽힌 부분이 적어 실패해도 옮기기 쉽다. 다만 실제 고객 정보, 비밀번호와 회사의 중요한 비밀은 넣지 않아야 기능 시험과 보안 검토를 분리할 수 있다.

아주 큰 프로젝트에서 여러 AI를 동시에 쓰는 팀은 속도보다 충돌을 먼저 살펴야 한다. 여러 AI가 같은 파일을 고치면 수정본은 빨리 늘어도 사람의 검토가 밀릴 수 있다. 누가 어느 부분을 맡는지, 어떤 작업을 먼저 해야 하는지 분명히 정하는 것이 단순한 수정 횟수보다 중요하다.

어떤 프로젝트든 나가는 방법을 준비해야 한다. 가격이 오르거나 서비스가 멈췄을 때 코드, 팀 댓글, 자동 검사 결과와 AI 작업 기록을 언제 어떤 파일로 받을 수 있는지 확인한다. 외부 사본을 정기적으로 만들고 복구 연습을 해 두면 편리함을 누리면서도 선택권을 지킬 수 있다.

Origin의 성패는 편리함보다 ‘되돌아갈 수 있느냐’가 가른다

앞으로 공개될 가격표와 운영 약속이 Origin의 첫 성적표가 된다. 무료 플랜 지원 여부, 기업 데이터가 저장되는 지역, 저장 한도, 장애 때 보상 기준이 나와야 회사용 서비스로 믿을 수 있는지 판단할 수 있다.

AI 여러 개가 동시에 일할 때 충돌을 얼마나 잘 풀어 주는지도 확인해야 한다. 실패한 검사를 스스로 고치는지, 사람의 승인을 반드시 거치는지, 왜 그런 수정을 했는지 기록이 남는지가 실제 가치다. 이 기능이 현장에서 안정적으로 작동해야 “AI 시대의 코드 보관 서비스”라는 설명이 마케팅을 넘어선다.

마지막 기준은 이동성이다. GitHub와의 양방향 동기화가 오래 유지되고, Origin에서 만든 저장소도 다른 서비스로 쉽게 옮길 수 있어야 한다. 코드뿐 아니라 팀 댓글과 검사 기록까지 내보낼 수 있다면 이용자는 떠날 수 있다는 확신을 가진 채 Origin을 선택할 수 있다.

Origin은 Cursor와 GitHub 사이를 오가던 불편을 줄여 준다. 그러나 편해진 출입문이 비상구까지 막아서는 안 된다. 원본을 따로 남기고, 최종 승인은 사람이 맡고, 언제든 복구할 수 있게 준비한 팀만이 이 새 기능을 안전한 생산성으로 바꿀 수 있다.
