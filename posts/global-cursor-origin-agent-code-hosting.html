Cursor Origin이 열린 날, AI 코딩은 저장소까지 내려왔다

AI 코딩 도구 Cursor가 자체 코드 호스팅 서비스 ‘Origin’을 유료 이용자에게 얼리 베타로 열었다. 6월에 예고한 제품이 실제 저장소 생성, 풀 리퀘스트, 코드 탐색, GitHub 양방향 동기화까지 갖추고 사용자 손에 들어온 것이다. 편집기 안의 보조 기능이던 에이전트가 이제 코드가 보관되고 검토되고 배포되는 관문까지 차지하기 시작했다.

Cursor는 8월 17일 공식 변경 기록에서 Origin을 모든 유료 플랜 이용자에게 순차적으로 제공한다고 발표했다. 엔터프라이즈 조직은 관리자가 사용을 거부할 수 있다. ‘출시’라는 말에는 범위가 붙는다. 정식 일반 제공이 아니라 기능과 운영 정책이 바뀔 수 있는 얼리 베타다.

이번에 새로 가능해진 일은 구체적이다. 이용자는 Cursor의 Codebase 탭에서 저장소를 만들고 전용 명령줄 도구로 기존 프로젝트를 밀어 넣을 수 있다. 저장된 코드를 탐색하고 검색하며, 풀 리퀘스트의 커밋과 검사 결과, 변경 파일을 보고 댓글을 남기거나 병합할 수도 있다.

Origin 자체가 처음 세상에 알려진 날은 아니다. Cursor는 6월 개발자 행사 Compile에서 에이전트 시대의 Git 호스팅을 예고했다. 따라서 이번 뉴스의 정확한 변화는 ‘새 아이디어 발표’가 아니라 ‘대기 명단 제품이 실제 유료 계정으로 풀리기 시작했다’는 데 있다.

코드 편집기와 저장소가 붙으면 무엇이 달라지나

지금까지 Cursor의 에이전트가 코드를 고쳐도 협업의 최종 기록은 대개 GitHub나 GitLab에 남았다. 계정 권한을 연결하고, 브랜치를 만들고, 풀 리퀘스트를 열고, 검사 결과를 다시 읽는 과정에서 제품 경계가 여러 번 바뀌었다. Origin은 그 경계를 한 회사의 데이터와 화면 안으로 당긴다.

Cursor는 각 저장소에서 에이전트에게 질문하고, 변경을 만들고, 풀 리퀘스트를 갱신하거나 새 브랜치를 밀어 넣을 수 있다고 설명한다. 사람의 편집 화면과 에이전트 실행 환경, 검토 이력이 같은 객체를 바라보면 문맥을 전달하는 비용이 줄어든다. 특히 여러 에이전트가 동시에 브랜치를 만드는 팀에서는 누가 어떤 근거로 무엇을 바꿨는지 연결하는 기능이 중요해진다.

그렇다고 Git이 사라지는 것은 아니다. Origin도 저장소와 브랜치, 커밋, 풀 리퀘스트라는 익숙한 단위를 사용한다. 변화는 버전 관리 형식보다 운영 주체에 있다. 소스 코드가 보관되는 곳과 AI가 코드를 읽고 쓰는 곳이 한 플랫폼으로 합쳐진다.

배포와 지속적 통합도 붙는다. 공식 발표에는 Vercel 미리보기 배포, Depot와 Buildkite의 검사 실행 연동이 포함됐다. 기존 GitHub Actions 워크플로는 Depot나 Buildkite를 거쳐 실행할 수 있다. 아직 GitHub Actions를 Origin이 그대로 호스팅한다는 뜻은 아니므로 실행 사업자와 비용 조건을 따로 확인해야 한다.

왜 GitHub를 버리지 않고 먼저 복제하나

Origin의 가장 현실적인 기능은 ‘GitHub 동기화’다. 조직을 연결하고 저장소를 선택하면 Cursor가 사본을 가져온다. 사용자는 Origin에서 코드를 찾아보고 당겨 올 수 있지만, GitHub에서 시작된 저장소의 푸시는 계속 GitHub로 가며 GitHub가 원본 기록을 유지한다.

풀 리퀘스트 댓글과 반응도 양방향으로 동기화된다. Cursor에서 댓글을 달면 GitHub에 올라가고, GitHub에서 남긴 답변은 Cursor에 나타난다. 기존 권한, 자동화, 감사 이력, 오픈소스 커뮤니티를 한 번에 옮기지 않고 에이전트 통합만 시험할 수 있게 한 완충 장치다.

이 접근은 GitHub의 거대한 네트워크를 인정한다. GitHub는 2025년 Octoverse에서 1억8천만 명이 넘는 개발자가 플랫폼을 사용한다고 밝혔다. 저장소 주소만 옮기는 것으로 이슈, 릴리스, Actions, 앱, 보안 규칙, 외부 링크까지 이동하는 것은 아니다.

동시에 Cursor에는 데이터를 자기 화면으로 끌어올 이유가 있다. 에이전트가 코드를 만들고 검토하는 순간을 더 많이 관찰하면 어느 변경이 통과했고 어디서 되돌아갔는지 학습할 수 있다. 저장소는 단순 파일 보관함이 아니라 AI 작업의 입력, 실행 기록, 평가 결과가 만나는 장소가 된다.

하필 GitHub 장애 직후였다는 의미

Origin 개방은 GitHub가 8월 17일 몇 시간 동안 광범위한 장애를 겪은 시점과 겹쳤다. Android Central은 웹, 코드 리뷰, 자동화와 Copilot이 영향을 받았고 원시 파일 다운로드 오류율이 한때 약 50%에 이르렀다고 전했다. 발표 타이밍이 개발자 관심을 끌기에 더없이 좋았던 이유다.

하지만 그 장애가 Origin 출시의 원인이었다고 볼 근거는 없다. 제품은 두 달 전에 이미 공개됐고 코드 호스팅은 며칠 만에 만들 수 있는 서비스가 아니다. 우연한 시간적 겹침과 인과관계를 구분해야 한다.

GitHub도 문제를 숨기지 않는다. GitHub는 저장소 생성과 API, 자동화, 대형 저장소 부하가 빠르게 늘어 2025년 10월부터 용량을 열 배 키우는 계획을 진행 중이라고 밝혔다. 5월 가용성 보고서는 AI 보조·에이전트 개발이 트래픽 증가의 큰 원인이라고 설명했다.

이 대목에서 Origin의 주장은 설득력을 얻는다. 사람 한 명이 하루에 몇 번 푸시하던 체계와 수십 개 에이전트가 계속 브랜치를 만들고 검사를 요청하는 체계는 부하 모양이 다르다. 그러나 ‘에이전트용’이라는 문구만으로 안정성과 처리량이 입증되지는 않는다. 공개 벤치마크, 실제 장애 기록, 서비스 수준 약정이 필요하다.

경쟁자는 GitHub 하나가 아니다

AI 시대의 코드 호스팅을 다시 만들려는 시도는 Cursor만의 것이 아니다. 전 GitHub CEO 토마스 돔케가 만든 Entire는 에이전트 세션과 코드 변경의 이유를 함께 기록하는 네트워크를 개발하고 있다. The Register는 Entire가 GitHub 저장소 미러와 독립 브랜치를 제공하며 향후 네트워크를 오픈소스로 공개할 계획이라고 보도했다.

GitLab, Bitbucket, Codeberg와 자체 호스팅 Git도 이미 존재한다. Origin의 차별점은 저장소 기능의 새로움보다 Cursor 에이전트와의 결합 강도다. 경쟁의 질문도 “누가 Git을 구현했나”가 아니라 “에이전트의 생성·검토·승인·감사 과정을 누가 가장 안전하게 연결하나”로 바뀐다.

여기에는 이해 충돌이 있다. 코드를 만드는 에이전트와 그 코드를 평가하는 검토 도구, 기록을 보관하는 호스트가 모두 같은 회사에 있으면 통합은 매끄럽다. 반대로 한 계층의 오류나 정책 변경이 전체 개발 흐름에 번질 수 있다. 독립된 검사와 외부 백업이 더 중요해지는 이유다.

아직 확인되지 않은 것

첫째는 가격이다. 현재 발표는 유료 플랜에 포함된 얼리 베타라고만 설명한다. 저장 용량, 네트워크 전송, 조직 좌석, CI 실행, 앱 사용량이 정식 출시 뒤 어떻게 과금될지 공개 정보가 충분하지 않다. 기존 Cursor 구독료만으로 장기 운영된다고 가정하면 안 된다.

둘째는 운영 보증이다. 베타 제품의 가용성 목표, 백업 주기, 데이터 복구 시간, 지역 선택, 고객별 암호화 키, 법적 보존 정책은 대기업 이전을 결정할 핵심 정보다. 일반적인 Cursor 보안 문서가 Origin 전용 서비스 약정의 빈칸을 자동으로 채우지는 않는다.

셋째는 데이터 사용이다. Cursor는 개인정보 보호 모드에서 코드 데이터를 모델 공급자가 저장하거나 학습에 쓰지 않도록 한다고 설명한다. 다만 Origin 자체 호스팅 저장소의 코드, Git 이력, 풀 리퀘스트와 에이전트 로그에 어떤 보존·학습 정책이 적용되는지는 계약 문서에서 저장소별로 확인해야 한다.

넷째는 내보내기다. Git 커밋과 브랜치는 다른 호스트로 밀어 넣기 쉽지만 풀 리퀘스트 댓글, 검사 이력, 앱 설정, 에이전트의 작업 이유는 Git 객체가 아니다. 팀이 떠날 때 무엇을 어떤 형식으로 가져갈 수 있는지가 실제 종속 비용을 결정한다.

핵심 판단: Origin은 GitHub를 하루아침에 대체한 제품이 아니라, Cursor가 편집기·에이전트에서 코드 보관과 검토 계층으로 내려온 사건이다. 현재 가장 가치 있는 사용법은 중요한 저장소를 즉시 이전하는 것이 아니라 GitHub 동기화로 통합 효과와 데이터 경계를 검증하는 것이다.

한국 개발팀이 바로 해볼 실험

첫 실험은 비핵심 저장소 하나를 GitHub와 동기화하는 것이다. 같은 작업을 기존 GitHub 화면과 Origin에서 각각 수행하고, 에이전트가 만든 브랜치와 풀 리퀘스트 댓글이 양쪽에 얼마나 빨리 정확하게 반영되는지 기록한다. 기능 데모보다 되돌리기 가능성을 먼저 본다.

두 번째는 권한표 작성이다. Cursor 계정, GitHub 앱, 조직 관리자, 저장소 읽기·쓰기, 배포 앱과 CI가 어떤 토큰을 공유하는지 그린다. 에이전트가 코드를 수정할 권한과 프로덕션 배포를 승인할 권한은 분리해야 한다.

세 번째는 장애 훈련이다. Origin에 접속할 수 없을 때 로컬 복제본에서 새 브랜치를 만들고 다른 원격 저장소로 푸시할 수 있는지 확인한다. GitHub 동기화가 멈췄을 때 어느 쪽 기록이 원본인지, 충돌한 풀 리퀘스트 댓글을 어떻게 처리할지도 정해야 한다.

네 번째는 품질 대조다. 같은 코드 변경을 Cursor 에이전트가 만들고 독립된 검사 도구가 검토하게 해 통합 플랫폼의 자기평가 편향을 줄인다. 자동 병합은 테스트 통과만이 아니라 보안 규칙, 코드 소유자 승인, 변경 규모 한도를 함께 만족할 때만 허용하는 편이 안전하다.

저장소 성격에 따라 답이 달라진다

오픈소스 프로젝트는 가장 신중해야 한다. 저장소 주소는 단순 보관 장소가 아니라 이슈 검색, 기여자 평판, 릴리스 다운로드, 문서 링크가 모인 공공 광장이다. Origin의 에이전트 기능이 편리해도 외부 기여자가 새 계정과 검토 화면을 배워야 한다면 프로젝트 전체의 거래비용은 오히려 커질 수 있다. 공개 프로젝트는 GitHub 원본을 유지한 채 관리자만 동기화 기능을 시험하는 방식이 현실적이다.

금융·의료·공공처럼 규제와 감사가 중요한 조직은 기능 목록보다 증거를 먼저 요구해야 한다. 어느 지역에 코드와 로그가 저장되는지, 하위 처리자는 누구인지, 관리자 열람과 삭제가 감사 기록으로 남는지, 보안 사고 통지가 몇 시간 안에 이뤄지는지가 도입 여부를 좌우한다. 일반 편집기 계약에 저장소 호스팅 책임이 자동으로 포함된다고 가정하지 말고 Origin 전용 조항을 확인해야 한다.

반대로 짧게 쓰고 버리는 내부 자동화나 새 실험 프로젝트는 좋은 시험장이 될 수 있다. 기존 앱과 커뮤니티 의존성이 적어 실패해도 이동 비용이 낮고, 에이전트가 만든 변경을 저장소 화면에서 바로 검토하는 이점을 빠르게 측정할 수 있다. 다만 시험 프로젝트라도 운영 비밀이나 실제 고객 데이터를 넣지 않아야 기능 평가와 보안 승인을 분리할 수 있다.

대형 모노레포와 다수 에이전트 팀은 처리량보다 충돌 관리부터 봐야 한다. 같은 파일을 여러 에이전트가 고치면 푸시 속도가 빨라도 사람의 검토 대기열이 쌓이고, 서로의 전제를 모른 채 만든 변경이 테스트를 반복해서 깨뜨릴 수 있다. Origin이 작업 의존성과 코드 소유권, 우선순위를 얼마나 잘 표시하는지가 단순 커밋 수보다 중요한 생산성 지표다.

구매 계약에는 종료 절차를 넣을 필요가 있다. 서비스가 중단되거나 가격이 바뀔 때 저장소와 풀 리퀘스트, 댓글, 검사 결과, 에이전트 로그를 어느 기간 안에 어떤 형식으로 받을 수 있는지 정한다. 정기적인 외부 미러와 복구 훈련을 계약상 권리로 남기면 플랫폼 통합의 편의성을 누리면서도 협상력을 잃지 않을 수 있다.

앞으로 볼 지표

가장 먼저 볼 것은 베타 접근 범위와 가격표다. 무료 플랜 지원, 엔터프라이즈 지역, 저장·전송 한도, 서비스 수준 약정이 공개되면 취미 프로젝트가 아닌 조직용 호스트로서 위치를 가늠할 수 있다.

다음은 에이전트 네이티브 기능의 실체다. 동시 작업 수, 브랜치 충돌 해결, 실패한 검사 자동 수정, 사람 승인 지점, 작업 이유 보존이 실제 제품으로 제공돼야 ‘AI 시대의 Git 포지’라는 표현이 마케팅을 넘어선다.

마지막은 이동성이다. GitHub 양방향 동기화가 오래 유지되는지, 자체 호스팅 저장소를 다른 서비스로 옮기는 도구가 나오는지, 풀 리퀘스트와 감사 로그까지 내보낼 수 있는지 봐야 한다. 가장 좋은 에이전트 플랫폼은 사용자를 붙잡는 곳이 아니라 떠날 수 있다는 확신을 주면서 남게 하는 곳이다.

필자의 결론은 Origin의 진짜 경쟁 상대가 GitHub 화면이 아니라 개발 과정의 분절이라는 것이다. 저장소와 에이전트가 붙으면 속도는 빨라질 수 있다. 그 속도를 믿을 수 있는 기록, 분리된 승인, 복구 가능한 데이터로 바꾸는 팀만이 이번 변화를 생산성으로 가져갈 수 있다.
