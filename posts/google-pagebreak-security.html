AI와 보안 · 2026.09.24 구글 자체 결과 발표

구글, AI로 자사 웹서비스의 보안 허점 500개 넘게 찾았다고 밝혔다

구글이 내부 보안 AI인 페이지브레이크로 자사 웹서비스에서 특정 종류의 보안 허점 500개 이상을 찾았다고 발표했다. AI가 의심되는 곳을 찾으면 별도 검사 프로그램이 실제 문제가 생기는지 확인한다. 그럴듯한 경고를 많이 보내기보다, 재현되는 문제를 골라 담당자에게 전달하는 방식이다. 발표·사례 원문

AI의 의심을 그대로 담당자에게 보내지 않았다

보안 AI가 멀쩡한 코드를 위험하다고 잘못 알려 주면 담당자가 일일이 확인해야 한다. 틀린 경고가 쌓일수록 실제 문제를 고칠 시간이 줄어든다.

구글의 페이지브레이크는 역할을 나눴다. AI가 코드를 읽으며 문제가 될 만한 부분을 찾고, 별도의 검사 프로그램이 실제 실행 결과를 확인한다. 이 확인 프로그램은 AI가 매번 그때그때 만들어 내는 답변이 아니라 사람이 마련한 검사 로직을 사용한다. 페이지브레이크의 구조와 발견 결과

AI가 “이 부분이 위험해 보인다”고 지목하면 검사 프로그램이 실제로 시험한다. 같은 조건에서 문제가 다시 생기는지 확인한 뒤, 확인된 결과를 개발자에게 보낸다.

500개는 무엇을 센 숫자일까

구글은 자사 웹서비스에서 XSS라는 종류의 보안 허점을 500개 넘게 찾았다고 밝혔다. 보안 허점은 공격자가 악용할 수 있는 프로그램의 문제를 말한다. 500개는 이번에 발견한 XSS 문제의 수다. 페이지브레이크의 구조와 발견 결과

XSS는 웹페이지에 들어온 내용을 안전하게 처리하지 못해 다른 사람의 브라우저에서 원치 않는 코드가 실행될 수 있는 문제다. 브라우저는 우리가 인터넷 페이지를 여는 프로그램이다. 게시판에 쓴 내용은 글로 보여야 하는데, 그 일부를 실행 명령처럼 받아들이면 문제가 생길 수 있다.

이런 문제는 게시판 외에도 웹서비스가 입력받은 내용을 화면에 보여 주는 여러 곳에서 생길 수 있다. 피해 범위는 문제가 있는 기능과 그 기능이 접근할 수 있는 자료에 따라 달라진다.

구글은 내부 코드와 검사 도구를 이용해 자사 서비스를 점검했다. 이 작업에는 내부 자료를 읽고 시험할 권한이 필요하다. 일반 제미나이 이용자에게 공개된 기능은 아니다.

오래 쌓아 둔 검사 도구에 AI를 연결했다

페이지브레이크의 성과를 새 모델 하나의 능력으로만 설명하면 중요한 부분이 빠진다. 구글은 기존의 보안 검사 도구와 내부 개발 자료를 함께 활용한다고 설명했다. AI가 알아낸 의심을 실제 서비스에서 확인할 수 있는 환경이 이미 갖춰져 있다는 점이 중요하다.

구글은 오래전부터 웹서비스의 취약점을 검사하는 도구와 그 검사 도구를 시험하는 자료를 만들어 왔다. 과거에 공개한 파이어링 레인지도 보안 검사기가 어떤 문제를 잡는지 시험하기 위한 프로젝트다. 이번 발표는 그런 기존 검사 기반 위에 AI가 의심 지점을 찾는 능력을 더한 것으로 이해할 수 있다. 구글의 웹 보안 검사 도구 연구 배경

검사 도구 자체도 시험이 필요하다. 알려진 문제를 넣은 예제에서 제대로 경고하는지, 안전한 예제를 잘못 위험하다고 판단하지 않는지 비교할 수 있다. AI가 더 많은 후보를 찾더라도 확인 단계가 불안정하면 담당자가 결과를 믿기 어려워진다.

구글의 보안 신호 연구는 실제 웹 요청에서 보안 관련 정보를 모아 서비스의 상태를 파악하는 방법을 다룬다. 웹 요청은 브라우저가 서버에 페이지나 자료를 달라고 보내는 메시지다. 어떤 요청이 어떤 서비스와 관련되는지 알면 조사할 대상을 좁히는 데 도움이 된다. 보안 정보를 모으는 Security Signals 연구

구글은 내부 코드와 서비스가 어떻게 연결되는지 보여 주는 자료도 활용했다. 다른 회사가 비슷한 검사를 하려면 자기 코드와 검사 도구를 준비하고 필요한 접근 권한을 설정해야 한다.

틀린 경고가 적다는 것과 모든 문제를 찾는 것은 다르다

구글은 문제를 재현한 뒤 경고를 보내면서 잘못된 경고를 거의 없앴다고 밝혔다. 구글이 자체 운영 결과로 발표한 수치다. 페이지브레이크의 구조와 발견 결과

잘못된 경고와 놓친 문제는 서로 다르다. 정상적인 프로그램에 위험하다고 표시하면 잘못된 경고다. 실제 위험한 문제가 있는데 아무 알림을 내지 못하면 놓친 문제다. 전자가 적다고 후자도 자동으로 적어지는 것은 아니다.

페이지브레이크도 검사 도구가 아직 다루지 못하는 유형이나 복잡한 상황이 있다고 설명한다. AI가 의심했지만 확인하지 못한 후보는 이후 조사와 검사 도구 개선에 활용한다. 담당 제품팀에 즉시 보내는 경고와 내부에서 더 살펴보는 후보를 나누는 것이다. 페이지브레이크의 구조와 발견 결과

이 차이는 보안 담당자의 시간을 어떻게 쓸지와 연결된다. 근거가 약한 보고서를 모두 받으면 진짜 문제를 고치는 시간이 줄 수 있다. 반대로 확인되지 않았다는 이유로 의심을 모두 버리면 새로운 유형의 문제를 놓칠 수 있다. 전달할 결과와 연구할 후보를 분리하면 두 일을 구분할 수 있다.

성능을 볼 때는 발견한 문제 수, 틀린 경고 수, 놓친 문제 수를 각각 봐야 한다. 페이지브레이크는 AI가 찾은 의심 지점을 실제로 시험해 틀린 경고를 줄이는 데 초점을 맞췄다.

발견 뒤에는 고치고 다시 시험하는 일이 남는다

보안 허점을 찾으면 개발자는 수정 코드를 만들고 기존 기능이 계속 작동하는지 확인해야 한다. 문제가 있던 동작을 막았는데 정상 이용자도 로그인하지 못하게 됐다면 좋은 수정이라고 보기 어렵다. 발견한 문제를 없애는 것과 서비스를 계속 사용할 수 있게 하는 것을 함께 봐야 한다.

구글은 페이지브레이크와 수정 작업을 담당하는 다른 AI 프로젝트의 연결을 더 깊게 하겠다고 설명했다. 그중 코드멘더는 소프트웨어의 문제를 찾고 수정 코드를 제안하는 서비스다. 7월에 시험 공개된 별도 제품이며, 페이지브레이크가 누구에게나 공개됐다는 뜻으로 섞어 읽으면 안 된다. 페이지브레이크의 구조와 발견 결과 수정 코드를 제안하는 코드멘더 소개

코드멘더 소개는 코드 조사, 문제 확인, 시험한 수정안 제공을 이어 붙이는 방향을 설명한다. 개발자가 검토에 참여한다는 조건도 남아 있다. AI가 수정안을 작성하는 일과 회사의 실제 서비스에 그 수정을 적용하는 일은 다른 단계다. 수정 코드를 제안하는 코드멘더 소개

도구를 도입할 기업은 경고가 실제 수정으로 이어졌는지 살펴보면 된다. 담당자가 같은 문제를 확인할 수 있었는지, 수정 후 문제가 사라졌는지, 다른 기능은 정상인지 확인하는 것이다.

우리 서비스의 보안을 맡길 때도 역할을 나눈다

개발팀이 AI에 코드를 살펴보게 한다면 첫 결과를 최종 판정으로 쓰기보다 조사할 후보로 받을 수 있다. 어느 파일의 어떤 처리에서 위험을 의심하는지 설명하게 하고, 팀이 허용한 시험 환경에서 확인하는 것이다. 타인의 서비스에 허락 없이 시험하는 일로 확대해서는 안 된다.

시험 환경은 실제 고객에게 영향을 주지 않도록 별도로 준비한 곳이다. 샘플 자료와 테스트 계정으로 정상 동작과 의심되는 조건을 비교하면 된다. 어떤 도구에 어떤 권한을 주는지는 개발팀이 정하고, 외부 서비스나 실제 고객 정보에 미치는 영향을 먼저 살펴야 한다.

수정안을 받을 때는 어떤 코드를 왜 바꿨고 무슨 시험을 했는지 함께 남긴다. 다음 검토자가 그 기록을 보고 수정 내용을 판단할 수 있어야 한다.

이번 발표는 구글이 자사 서비스의 보안 허점을 찾은 방법과 결과를 소개한 내용이다. 이용자에게 비밀번호 변경을 요청한 공지는 없다.

페이지브레이크에서는 AI가 의심 지점을 찾고, 별도 프로그램이 시험하고, 개발자가 확인된 문제를 고친다. 이처럼 실제 시험 결과를 함께 보내면 개발자가 어떤 문제부터 고칠지 판단하기 쉬워진다.
