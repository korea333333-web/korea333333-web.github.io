Slack, 클로드·코파일럿이 짠 코드를 팀 채널에서 함께 고치는 ‘Slack Code’ 공개

Slack이 Claude·Devin·GitHub Copilot·Vercel 같은 AI 코딩 도구의 작업을 팀 채널에서 함께 보고 고치는 ‘Slack Code’를 공개했다. 개발자 한 명이 AI에게 일을 맡긴 뒤 결과만 전달하는 대신, 제품 담당자와 디자이너도 AI의 계획과 수정 내용을 보며 방향을 바꾸거나 작업을 멈출 수 있다. 다만 Slack 화면에서 함께 봤다는 이유만으로 코드가 안전해지는 것은 아니다. 코드와 변경 기록을 보관하는 저장소의 접근권, 테스트와 실제 서비스 배포 승인은 기존 담당자에게 그대로 남는다.

Slack의 공식 발표와 사용 도움말을 보면 사용법은 이렇다. 버그 신고나 고객 불만이 적힌 Slack 대화에서 지원되는 AI를 부르면, 그 일만 다루는 코드 채널이 생긴다. AI의 계획, 코드 차이(diff·어느 줄이 바뀌었는지 보여 주는 비교), Canvas, HTML 실행 미리보기와 관련 파일·링크가 한곳에 모인다.

2026년 8월 24일 기준 실제 코드 채널을 만들 수 있는 도구는 Anthropic의 Claude, Cognition의 Devin, GitHub Copilot, Vercel 네 가지다. Salesforce 발표에는 ChatGPT도 창립 파트너로 나오지만, Slack 공식 블로그는 OpenAI 지원을 ‘곧 제공’이라고 적었다. 현재 도움말의 지원 목록에도 ChatGPT는 없다. 발표 파트너와 지금 바로 쓸 수 있는 제품을 같은 것으로 보면 안 된다.

Slack 공식 블로그의 발표일은 8월 20일이다. 별도 공식 시각은 적혀 있지 않지만 VentureBeat는 8월 20일 오후 5시 미국 태평양시간, 한국시간으로 21일 오전 9시에 소식을 전했다. 전날까지는 개발자가 AI 결과를 복사해 팀에 보고하는 일이 흔했다. 이제는 한 번의 AI 작업이 시작되고 끝날 때까지의 기록인 ‘에이전트 세션’을 팀이 처음부터 같이 보며 지시하고 검토할 수 있다.

결과만 보내는 대신 만드는 과정을 같이 본다

예를 들어 쇼핑몰 결제 버튼이 눌리지 않는다는 신고가 Slack에 올라왔다고 하자. 예전에는 개발자가 혼자 AI에게 수정을 시키고, 끝난 뒤 바뀐 파일과 화면을 팀에 다시 설명했다. Slack Code에서는 그 대화에서 바로 코드 채널을 열고 제품 담당자는 요구사항을, 디자이너는 화면을, 개발자는 구현과 보안을 같은 자리에서 확인한다.

일반 채팅방에서는 대화만 보이지만, 코드 채널에서는 삭제된 줄과 새로 생긴 줄을 나란히 보여 주는 diff, AI의 계획, 실행 화면을 따로 볼 수 있다. 팀원은 “버튼 색은 맞지만 결제 오류는 고쳐지지 않았다”처럼 화면과 코드를 보며 구체적으로 다시 지시할 수 있다.

Claude나 Devin 같은 지원 AI를 부르면 작업용 코드 채널이 만들어진다. 일이 끝나면 사용자가 직접 닫거나 보관할 수 있고, 7일 동안 아무 활동이 없으면 사이드바에서 자동으로 빠진다. 보관은 삭제가 아니다. 새 대화는 막되 기존 작업 내용은 워크스페이스 보존 정책이 허용하는 동안 다시 찾을 수 있다.

이 기록에는 AI가 왜 특정 라이브러리를 바꿨는지, 누가 요구사항을 수정했는지, 어떤 미리보기를 보고 승인했는지가 남는다. 코드와 변경 이력을 함께 보관하는 온라인 공동 폴더인 ‘저장소’의 기록만으로 설명하기 어려운 결정 이유를 보완하는 셈이다. 대신 고객 이름이나 장애 로그처럼 민감한 내용도 남을 수 있어 검색 권한과 보존 기간을 함께 정할 필요가 있다.

Slack 요금만 내면 모든 AI를 쓸 수 있는 것은 아니다

Slack Code는 지원 AI가 설치된 모든 Slack 구독에서 일반 멤버에게 제공된다. 하지만 Claude나 Devin 같은 파트너 계정, 필요한 요금제와 사용량 비용, 관리자의 설치 승인은 따로다. 게스트는 Slack의 AI 앱과 에이전트를 직접 쓸 수 없다. 무료 Slack 워크스페이스를 쓴다고 유료 코딩 AI의 이용량까지 무료로 따라오는 구조가 아니다.

팀이 실제로 내는 돈에는 Slack 좌석 요금 외에도 AI 이용료, 코드 실행 환경, 저장소 연결, 미리보기 서버, 보안 검사와 사람의 검토 시간이 들어간다. 코드가 바뀔 때 자동으로 검사를 돌리는 지속적 통합(CI)과 실제 고객이 쓰는 프로덕션 서비스도 따로 연결된다. 여러 AI를 설치하면 어떤 일은 Claude에, 어떤 일은 Copilot에 보낼지도 정한다. 화면 하나로 모였다고 가격표까지 하나가 되는 것은 아니다.

Computerworld의 출시 보도와 현재 Slack 도움말은 Claude·Devin·Copilot·Vercel을 바로 쓸 수 있는 목록으로 설명한다. ChatGPT는 창립 파트너지만 아직 ‘곧 제공’ 단계다. 네 도구도 필요한 요금제와 관리자 설정, 저장소와 실행 환경 권한이 모두 다르다.

지역이나 회사 계약에 따라 설치 화면에 보이는 기능도 달라질 수 있다. 구매할 때는 발표 이미지보다 지금 사용하는 계정의 설치 화면, 관리자 문서와 각 파트너의 약관을 보는 편이 정확하다. ‘모든 Slack 구독에서 제공’이라는 문장은 협업 화면을 뜻하지, 모든 AI 사용권을 뜻하지 않는다.

AI가 빨라질수록 팀은 검토에서 막힌다

AI는 짧은 시간에 많은 코드를 바꿀 수 있다. 문제는 동료가 왜 바뀌었는지 이해하고 안전한지 확인하는 데 더 오래 걸린다는 점이다. Slack Code는 고객 불만이 적힌 원래 대화와 수정 작업을 붙여 두어, 검토자가 배경부터 다시 찾아 읽는 시간을 줄이려 한다.

제품 담당자는 고객이 무엇을 불편해했는지 직접 설명하고, 디자이너는 실행 화면에서 색과 동선을 지적할 수 있다. 개발자는 diff와 테스트를 본다. 하지만 비개발자가 AI에 의견을 줄 수 있다는 것과 저장소를 바꿀 권한이 있다는 것은 전혀 다른 문제다.

비슷한 오류가 다시 생기면 보관된 코드 채널에서 당시 증상과 선택한 해결책, 반대 의견을 함께 찾을 수 있다. 코드 변경 기록이 ‘무엇이 바뀌었는지’를 남긴다면 코드 채널은 ‘왜 바꿨고 누가 받아들였는지’를 덧붙인다.

모든 작은 작업을 공개 채널로 만들면 오히려 읽을 것이 너무 많아질 수 있다. AI의 긴 계획과 중간 결과가 쌓이면 중요한 결정이 다시 묻힌다. 어떤 크기의 프로젝트에 채널을 만들지, 누구에게 알릴지, 끝날 때 어떤 요약을 남길지 정해야 공동 작업이 소음으로 변하지 않는다.

채널에 들어왔다고 모두 같은 권한을 갖는 것은 아니다

코드 채널을 누가 볼 수 있는지는 Slack의 공개 범위와 관리자 설정을 따른다. 그러나 실제 코드를 읽고 바꾸거나 배포하는 권한은 연결한 서비스마다 다르다. Claude Tag의 조직 신원, GitHub 계정, Vercel의 제한된 신원과 승인자 계정 가운데 누구의 자격으로 행동하는지 따로 확인하는 과정이 필요하다.

같은 채널에서도 한 사람은 저장소에 쓸 수 있고 다른 사람은 읽기만 할 수 있다. 게스트는 AI 앱을 직접 부르지 못하지만, 다른 사람이 공유한 결과를 어디까지 볼 수 있는지는 채널 설정에 달려 있다. 여러 사람이 같은 AI 작업을 조종할 때 최종적으로 누구의 저장소·배포 권한이 쓰이는지 보여 주지 않으면 사고 뒤 책임을 가리기 어렵다.

AI에 보내는 대화에는 고객 이름, 장애 로그, 비밀 URL, 화면 캡처와 미공개 제품 계획이 들어갈 수 있다. Slack 채널 권한을 물려받는다고 각 AI 회사의 데이터 보관 기간과 학습 제외 정책까지 같아지는 것은 아니다. Slack에서 파트너 AI로 어떤 정보가 넘어가고 어디에 남는지도 함께 보는 게 안전하다.

보관된 채널은 좋은 감사 자료가 될 수 있지만 영원히 남는다는 뜻도 아니다. 무료 플랜의 검색 범위, 기업의 eDiscovery와 법적 보존, 개인정보 삭제 요청, 퇴사자 권한 회수에 따라 기록의 수명이 달라진다. 금융·의료처럼 규제가 강한 분야라면 단순히 검색되는지를 넘어 누가 언제 열었는지 증명할 수 있어야 한다.

한 문장으로 보면: Slack Code는 AI가 코드를 더 잘 짜게 만드는 기능이 아니라, AI가 무엇을 바꿨는지 팀이 함께 보고 멈추고 승인하도록 만드는 협업 기능이다. 진짜 성패는 생성 속도보다 잘못된 변경을 얼마나 빨리 막고 승인 이유를 분명히 남기느냐에 달렸다.

미리보기가 멀쩡해도 검토를 건너뛰면 안 된다

diff는 어떤 줄이 바뀌었는지는 보여 주지만, 실행하지 않은 기능의 오류나 외부 부품의 보안 취약점, 데이터 이전 위험까지 자동으로 찾아 주지는 않는다. HTML 미리보기도 화면이 깨졌는지 확인하는 데는 좋지만 접근성, 속도, 서버 상태, 로그인과 결제가 제대로 작동하는지는 보증하지 않는다.

AI가 만든 코드도 지속적 통합(CI), 즉 코드가 바뀔 때 자동으로 돌리는 검사를 통과하는 조건은 그대로다. 단위·통합·브라우저 테스트, 타입과 린트, 비밀정보 탐지, 의존성 검사와 배포 전 환경 검증을 승인 조건으로 둔다. 채널에서 “좋아 보인다”는 말만으로 풀 리퀘스트(PR·바뀐 코드를 원본에 합쳐도 되는지 동료에게 묻는 검토 요청)가 실제 고객이 쓰는 프로덕션 서비스에 이어져서는 안 된다.

AI가 한 번에 너무 많은 파일을 바꾸면 사람은 겉만 보고 승인하기 쉽다. AI가 요구사항, 수정한 파일, 실행한 테스트, 남은 위험과 되돌리는 방법을 짧게 제출하게 하면 판단이 쉬워진다. 승인 버튼이 있다는 사실보다 승인자가 읽을 자료가 있는지가 중요하다.

처음 도입할 때는 AI에게 작업용 브랜치를 만들고 PR을 여는 일까지만 허용하는 편이 안전하다. 원본에 합치는 병합과 실제 서비스 배포는 기존 보호 규칙과 담당자에게 남긴다. Slack의 공식 설명도 배포처럼 위험이 큰 행동은 전문가의 승인을 거치도록 제시한다.

한국 팀은 작은 화면 오류부터 시험하면 된다

첫 시험은 재현 방법과 화면 캡처가 있는 작은 프런트엔드 오류가 알맞다. 한 사람은 요구사항, 한 사람은 diff, 한 사람은 실행 화면을 확인한다. AI가 문제를 정확히 이해했는지와 역할마다 무엇을 놓치는지를 기록하면 이 기능이 팀에 실제로 도움이 되는지 보인다.

다음은 권한 시험이다. 개발자와 제품 담당자 계정으로 같은 작업을 지시하고, 게스트 계정에서는 AI 호출이 막히는지 확인한다. 읽기 권한만 있는 사람이 코드 수정을 명령했을 때 거부되는지, 채널 밖의 비공개 저장소 정보를 AI가 가져오지 않는지도 살펴야 한다.

일부러 실패도 만들어 본다. 모호한 요구를 주거나 두 사람이 서로 다른 지시를 내리고, 테스트 실패와 긴 작업을 발생시킨다. 누가 AI를 멈출 수 있는지, 중간 수정이 작업용 브랜치에 남는지, 다시 시작할 때 어느 대화를 기억하는지 확인해야 사고 대응 방법을 알 수 있다.

마지막으로 같은 일을 개인 개발 프로그램(IDE) 안의 코딩 AI와 Slack Code에서 각각 해 본다. 생성 시간, 검토 대기, 다시 고친 횟수, AI 사용량과 팀 전체의 검토 시간을 비교한다. 작업이 잘 보이더라도 알림과 회의가 더 늘었다면 전체 생산성은 오히려 낮아질 수 있다.

Slack은 AI 모델보다 ‘일이 모이는 자리’를 잡으려 한다

Slack Code가 새로운 코딩 모델을 만든 것은 아니다. 여러 회사의 AI를 팀 대화와 검토·승인 과정에 모으는 역할을 맡는다. 어떤 AI가 코드를 쓰더라도 문제의 배경, 사람의 피드백과 결정 기록이 Slack에 남으면 협업 플랫폼의 영향력은 커진다.

팀은 Claude, Devin, Copilot, Vercel 가운데 일에 맞는 도구를 고를 수 있다. 반면 중요한 판단과 감사 기록이 코드 채널에 계속 쌓이면 다른 협업 도구로 옮길 때 대화까지 함께 내보내기 어려울 수 있다. 여러 AI를 고르는 자유와 Slack에 기록이 묶이는 위험이 동시에 생긴다.

GitHub, Microsoft Teams, Atlassian과 다른 개발 도구도 같은 자리를 노릴 수 있다. 코드 저장소에서 시작할지, 업무 티켓이나 대화에서 시작할지에 따라 AI가 읽는 정보와 사람이 통제하는 방법이 달라진다. Slack의 경쟁력은 채팅 화면 자체보다 저장소·CI·배포·보안 시스템을 얼마나 정확히 잇는지에서 갈린다.

다음 변화는 설치 범위·권한·기록·코드 품질에서 보인다

현재 네 AI가 어느 요금제와 지역에서 설치되는지, 기능과 사용량 제한이 어떻게 다른지가 첫 기준이다. ChatGPT는 Slack 공식 블로그가 ‘곧 제공’이라고 했으므로, 도움말 목록과 실제 설치 화면에서 코드 채널 생성이 확인되는 때가 다음 변화다.

공동 채널의 명령이 누구의 계정으로 저장소와 실행 환경에 접근하는지도 중요하다. 게스트와 봇은 어디까지 가능하고 승인 기록은 누구에게 돌아가는지 화면과 문서에서 분명하게 보여 줘야 한다.

대화, 계획, diff, 미리보기와 승인 기록을 표준 형식으로 내려받을 수 있는지도 봐야 한다. Slack의 보존 기한이 끝난 뒤에도 Git 변경 기록과 배포 기록에서 결정 근거를 이어 볼 수 있어야 한다.

마지막 성적표는 실제 코드 품질이다. 오류와 되돌림 비율, 검토 시간, PR 크기, 보안 문제와 비개발자의 지시 때문에 다시 한 일을 측정한다. 팀에 공개됐다는 사실만으로 코드가 좋아지지는 않는다.

Slack Code의 핵심은 “누구나 코딩한다”가 아니다. 빠르게 일하는 AI를 여러 사람이 이해하고 멈추고 책임질 수 있게 만드는 기능이다. 좋은 코드 채널은 AI가 말을 많이 남기는 곳이 아니라, 팀이 무엇을 바꿨고 왜 받아들였는지를 누구나 짧게 이해할 수 있는 곳이다.
